Which constructor runs, vs. when it runs

Last lesson said a constructor runs automatically, then immediately showed you a table where you pick which of two constructors fires. Can both be true?

Can you decide when the constructor runs? No.
Can you decide which constructor runs? Yes.

Those are two different questions, with two different answers. The lesson never separated them — here's the split.

"When" is not up for negotiation

An ordinary member function is called on its own line, whenever you feel like it:

Node n1;        // create it — line 1
n1.passed();     // call a function on it — line 2, separate moment
n1.passed();     // call it again — allowed, no limit

A constructor doesn't get that second line. There is no n1.Node(10); you write afterward — try it and it won't compile. Writing new Node(10) is the trigger; there's no separate "now construct it" step for you to place earlier or later, and no way to fire it a second time. That's the whole content of "automatic": construction is welded to the creation line, not scheduled by you.

"Which" is entirely up to you

Node declares two functions that happen to share the name Node:

Node(int newItem);   // one parameter
Node();               // zero parameters

Two functions allowed to share one name, distinguished only by their parameter list, is called overloading — it works for constructors and for ordinary functions alike. The compiler looks at what you typed and counts/matches the arguments: new Node(10) has one int argument, so it's an exact match for Node(int); new Node supplies none, so it matches Node(). That match is decided the instant the compiler reads your line — nothing runtime, nothing dynamic. You chose the constructor the moment you chose what to type.

A vending machine. Press B4, and the machine dispenses immediately — there's no separate "go" button after B4; pressing the button is the trigger, and it fires exactly once. That's "when," and it's fixed by the machine, not you. But B4 gives you chips and C2 gives you a soda — which item comes out is entirely decided by which button your finger picked. Same machine, same instant-dispense behavior, different result depending on your choice of button. new Node(10) and new Node are two different buttons on the same machine.

This is why the table in Lesson 6f had a "which constructor runs" column but never a "when" column — when is identical for every row: automatically, at new, exactly once. Only which changes, and it changes because the argument list you wrote changes.

So the original sentence still holds exactly as written: the constructor runs automatically, once, at creation. "Automatic" was only ever a claim about when. It was never a claim that you have no say in the matter at all — you still pick which recipe that automatic, unskippable moment follows, by what you write to the right of new.

Quick check — Node has Node(int) and Node(). What decides which one runs for a given new expression?

Right — the compiler matches your argument list to a parameter list at the moment it reads your new line. Declaration order and a separate call don't come into it.
Look at what changes between new Node(10) and new Node in the table above — it's the argument list, not the order the constructors were declared in, and there's no separate call line for either.

Second check — one word (yes/no): can you write code that runs Node::Node(int) a second time on a Node that already exists?

No — a constructor only ever runs at the creation instant. "Which" is your choice; "again, later, on demand" is not on offer at all.
Re-read "When is not up for negotiation" above — n1.Node(10); doesn't compile. There's no line of code that re-triggers a constructor on an existing variable.
