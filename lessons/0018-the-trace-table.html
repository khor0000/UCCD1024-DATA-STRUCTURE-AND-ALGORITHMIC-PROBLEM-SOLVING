Day 2 · Midterm Q1a — "given code, state the output"

The trace table

To find a loop's output on paper, draw a table with one column per variable and one row per pass. Fill it in one row at a time. Never do it in your head.

That is the lesson. The rest is the method and one worked example.

Why this is worth a lesson when you already know loops. Q1a does not test whether you understand for. It tests whether you can produce the exact printed output without a compiler. People lose these marks by being too fast — they read the loop, feel confident, and are off by one. The table removes the guessing. It is slower, and that is the point.

The method

  1. One column for every variable the loop touches. One extra column: OUTPUT.
  2. Write the starting values in row 0, before the loop runs.
  3. For each pass: check the condition first. If false, stop. If true, run the body and add a row.
  4. Write down every single cout, exactly as it prints — including whether there is a space, a newline, or nothing between items.
  5. Your answer is the OUTPUT column, read top to bottom.

Worked example

int total = 0;
for (int i = 1; i <= 4; i++) {
    total = total + i;
    cout << i << ":" << total << " ";
}
cout << "end";

The row that earns the marks

Row 5 is the one people skip. The loop does not stop after the body runs with i at 4 — it increments to 5, tests, then stops. Writing that row down is what stops off-by-one errors.

A turnstile you must walk into to find out it's locked. You don't stop one step early because you guessed it would be locked. You step up, it refuses, and only then do you turn around. The failed check is a real event. Give it a row.

When the tested variable changes inside the body

The example above is the easy shape: i is a counter, and the for header changes it. Q1a also uses a harder shape — the variable in the condition is changed by the body itself:

int n = 20;
while (n > 1) {
    n = n / 2;
    cout << n << " ";
}

Here is the trap, and it is the most common way this question is failed:

The condition asks what is, never what will be. It is a doorman checking your ticket as you arrive. He does not care what your ticket will say in a minute. If it is valid now, you go in — even if going in is what makes it invalid.

So when n is 2, the check is 2 > 1. That is true. The body runs, n becomes 1, and 1 is printed. It is very tempting to stop at 2 by reasoning "the next one would be 1, and 1 isn't greater than 1" — that reasoning tests the wrong value and costs the mark.

This is exactly why the table has a condition column. Filling that column makes you write down the value being tested, so you cannot substitute a prediction for it. Two rules follow:

  • Copy n's value into the row before you run the body. That is the value the condition sees.
  • Only stop when you have written a row whose condition column says false. If you stopped without writing that row, you have not finished the trace.

Critical Exam Trap • Testing The Next Value

The condition is checked against the variable's value right now, at the top of the loop — not against the value the body is about to give it. Stopping one pass early is the most common way Q1a is failed.

The stopping rule: you have not finished a trace until you have written a row whose condition column reads false.

Correct reasoning (earns marks)Incorrect reasoning (loses marks)
"n is 2. Is 2 > 1? Yes — run the body.""n would become 1 next, so stop now."

You might reasonably wonder: do I really lose a mark for a missing space? Assume yes and write it correctly. The table costs you nothing once you are used to it.

Quick check

Trace it on paper first, then type the exact output:
int i = 2;
while (i < 8) { cout << i << " "; i = i + 2; }

Correct. i reaches 8, the condition is false, and 8 is never printed. That last row is the one worth writing down.
Add one more row to your table for the pass where the condition fails. Does that pass print anything?
