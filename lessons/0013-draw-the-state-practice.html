Lesson 13 of the linked-list crash sequence · Midterm Q3a

Draw the state

Q3a does not ask you to write code. It hands you code and asks you to draw the chain it produces — boxes and arrows, on paper. This lesson is that one skill, drilled three times.

The only code you will see below is code you have already met: new Node, ->item, ->next, and assigning to a pointer. Nothing else. No new syntax appears in this lesson.

Before you start — 60 seconds, from memory

Retrieval check • before reading on

On paper, without scrolling back:

1. p is a pointer to a Node. Write the statement that reads that node's item.
2. n is a plain (non-pointer) Node variable. Write the statement that reads its item.
3. Write the one line that moves a pointer cur along to the next node.

reveal answers 
p->item      // pointer  → arrow
n.item       // plain variable → dot
cur = cur->next;

If any of those three did not come out, stop and re-read lesson 3 and lesson 6c before continuing. Everything below is built on them.

What you are drawing

Metaphor first: a Node is a railway carriage. It carries cargo (item), and it is coupled to the next carriage (next). A pointer like head is not a carriage — it is a signpost standing beside the track, saying "the front carriage is over there."

struct Node {
    int   item;
    Node *next;
};

So a drawing has exactly two kinds of mark, and mixing them up is the fastest way to lose the marks:

ThingHow you draw itWhy
a Nodetwo-cell box: item | nextit holds two fields
head, tmp, cur — any pointerone-cell box, arrow out of itit holds one thing: an address

You might reasonably wonder: why bother drawing the pointer as its own box at all — why not just draw an arrow from thin air? Because a pointer is a variable that lives somewhere and holds a value, exactly like an int does. The whole family of bugs in Exercise 3 only becomes visible once head has its own box you can watch change.

The method, three steps. (1) Draw the picture before you read any statement. (2) Do one statement, then redraw the whole picture. (3) Only then read the next statement. Do not hold two statements in your head at once — that is what loses the mark, every time.
Critical Exam Trap • Two Pointers Are Never One Box

When tmp and head hold the same address, it is tempting to draw a single box labelled head/tmp. They are two separate variables at two separate addresses that happen to hold equal values — exactly like int x = 5; int y = 5;. Merged into one box, the drawing can no longer show what tmp was for, and cannot show a step where one moves and the other does not. That step is usually the whole question.

Correct (earns marks)Incorrect (loses marks)
head at 0x900 and tmp at 0x904, both holding 0x500, both arrows converging on that node one box labelled head/tmp

Exercise 3 — drawing a state that is broken

Sometimes the code you are given is wrong, and you must draw what it actually produces, not what it was meant to produce. Start: a chain 10 → 20, with head holding 0x500. Someone writes this, meaning "put a new node 5 at the front":

Node *tmp = new Node;
tmp->item = 5;
head = tmp;          // line A
tmp->next = head;    // line B
On paper • two drawings, one per line

Draw the state after line A, then after line B. Take each line completely literally — a line reads whatever the variable holds at that moment, not what you intended it to hold.

reveal stage 1 — after line A, head = tmp;

Nodes 10 and 20 still physically exist, but no pointer anywhere holds 0x500. The program has permanently lost the way back to them — that is a memory leak. And walking this chain from head would print 5 forever, because cur = cur->next never moves anywhere.

step through the broken version, line by line

Your version — the same three lines, in the right order

This is what you wrote, and it is correct:

Node *tmp = new Node(50);
tmp->next = head;
head = tmp;

Step it and watch the one difference that matters: on line 2, head still holds the old first node's address, so the new node captures it before it is lost.

You might reasonably wonder: the two versions have the same two lines — why does order matter at all? Because head is a box holding one value. Writing into it destroys what was there. Line 2 in the broken version tries to read a value that line 1 already erased. Read before you overwrite.

Critical Exam Trap • Link The New Node Before Moving Head

When putting a node at the front, the new node must be linked to the old first node before head is changed. Once head has moved, the old address is gone and cannot be read back.

Correct (earns marks)Incorrect (loses marks)
tmp->next = head;
head = tmp;		 head = tmp;
tmp->next = head;
Produce it • closed book

Close this page. On paper, write the two lines that put a new node tmp at the front of a chain, in the correct order. Then say in one sentence why that order and not the other.

Exercise 4 — a sequence of list.insert / list.remove calls

This is the exact shape of Q3a(ii). The question gives you a series of whole-list operations — list.insert(at, x), list.remove(from) — and asks for the chain after each one. Positions are 1-indexed: position 1 is the head.

Start: empty list. Then:

list.insert(1, 3);
list.insert(2, 7);
list.insert(3, 5);
list.insert(4, 8);
list.remove(1);
list.remove(2);
On paper • one drawing per call, six in total

Draw the chain (values + arrows + NULL at the end) and write count after every line. Before each remove, re-number the nodes from head — 1, 2, 3… — and only then decide which node the number hits.

reveal — after the four inserts

3 → 7 → 5 → 8 → NULL, count = 4. Positions: 3 is 1, 7 is 2, 5 is 3, 8 is 4.

reveal — after list.remove(1);

Position 1 is the node holding 3. It goes. head now points at 7.

7 → 5 → 8 → NULL, count = 3. Re-number now: 7 is position 1, 5 is position 2, 8 is position 3.

reveal — after list.remove(2);

Position 2 — in the list as it stands now — is the node holding 5, not the original position-2 node. So 5 goes.

7 → 8 → NULL, count = 2.

If you got 5 → 8 here, you ran remove(1) twice: you deleted position 1, then deleted what was still labelled position 1 in your head instead of re-numbering.

Critical Exam Trap • Re-number After Every Call

Each call in the sequence acts on the list left behind by the one before it. The moment a node is removed, every node after it shifts down one position. remove(1) then remove(2) deletes the original 1st node and the original 3rd node — never the same node twice.

Correct (earns marks)Incorrect (loses marks)
re-count 1, 2, 3… from head immediately before each call, then apply it keep the position labels from the original list for the whole sequence
Produce it • closed book, fresh numbers

Close this page. Start from an empty list. Draw the chain and write count after each call:

list.insert(1, 4); · list.insert(2, 9); · list.insert(3, 6); · list.insert(1, 2); · list.remove(3); · list.remove(1);

reveal — final answer only (do the intermediate steps first)

After the inserts: 2 → 4 → 9 → 6 → NULL, count = 4 (the insert(1,2) puts 2 at the front).

After remove(3): position 3 is 9 → 2 → 4 → 6 → NULL, count = 3.

After remove(1): 4 → 6 → NULL, count = 2.
