Declaration vs definition, and ::

Last lesson ended with this, and something about it should have bothered you:

struct Student {
    string name;
    int    mark;
    bool   passed();     // ← where's the body?
};

There's a semicolon where { ... } should be. The function has no body. That's deliberate: a member function is written in two separate places, and this lesson is about both halves.

The two words themselves are easy to mix up — here's the hook that fixes it for good: de-FIN-ition = FINished. The definition is the finished, complete version — the actual body, the code that runs. A declaration is just a claim, like a customs declaration form: it says something exists and what shape it is, but hands over none of the substance. Same mapping as the menu below — menu = declaration, kitchen = definition.

Half 1 — the announcement (declaration)

bool passed(); inside the struct is a declaration. It announces that a function called passed exists, returns a bool, and takes no parameters. It does not say what the function does.

A restaurant menu, and the kitchen. The menu line "Nasi Lemak — RM8" tells you the dish exists, what it's called, and what it costs. It doesn't tell you how it's cooked. The recipe lives in the kitchen, out of sight, on a different piece of paper. The declaration is the menu line; the definition is the recipe.

Half 2 — the recipe (definition)

The body is written below the struct, on its own:

struct Student {
    string name;
    int    mark;
    bool   passed();          // menu line
};

bool Student::passed() {      // recipe
    return mark >= 50;
}

Read the second block piece by piece:

  • bool — the return type, repeated from the declaration.
  • Student:: — the new symbol. It says "this passed is Student's passed."
  • passed() — the name and parameters, repeated from the declaration.
  • { return mark >= 50; } — the body, which only exists here.

:: is called the scope resolution operator, and its whole job is answering "which struct does this function belong to?" Without it, the compiler would read bool passed() {...} as a brand-new outside function that has nothing to do with Student — and then mark inside it would refer to nothing.

bool passed()          { ... }   // an outside function, unrelated to Student
bool Student::passed() { ... }   // the body of Student's member function
:: is not . or ->. The dot and arrow are used at call time on a variable you have (a.passed()). :: is used at definition time on a struct type (Student::passed). There is no Student variable anywhere on that line — you're writing the recipe, not cooking a specific meal.

Why the declaration can leave parameter names out

This is the part that trips people up, and it's the exact shape you'll meet in List:

Node *find(int);

Compare it to something you already know from Lesson 3:

CodeWhat it is
Node *cur;A variable named cur that holds the address of a Node.
Node *find(int);A function named find that takes one int and returns the address of a Node.

The ( right after the name is the entire difference. Parentheses after a name mean function; no parentheses mean variable. The Node * at the front means the same thing in both cases — "a Node address" — it's just describing what the variable holds in one, and what the function hands back in the other.

(find is a real function from the List struct you'll meet next lesson. Ignore the name and what it does — only its shape matters here.) And the empty-looking (int): a declaration only needs the parameter's type, not its name, because a menu line doesn't need the recipe's variable names. The name appears in the definition, where it's actually used:

Node *find(int);                  // declaration: one int goes in. Name not needed.

Node *List::find(int position) {  // definition: NOW it needs a name, to use it
    ...uses position here...
}
Writing Node *find(int position); in the declaration is equally legal, and many people do it for readability. This course's List.h just leaves the names off. The two forms mean exactly the same thing — don't read anything into the difference.

Quick check — what does Node *find(int); declare?

Right — the parentheses make it a function. Node * at the front describes what it hands back.
Look for the parentheses. Node *cur; is a variable; Node *find(int); has (int) after the name, so it's a function that takes an int.

Second check — you're writing the body of Student's passed below the struct. What must go between bool and passed()? (Type it exactly.)

Exactly — Student::. Leave it out and you've written an unrelated outside function, and mark inside it refers to nothing.
Re-read the "recipe" block. Something sits between the return type and the function name, naming which struct owns it.

Next: one member function has a strange shape — no return type at all, and the same name as the struct itself.

Both halves, in one file

The same function is written twice, in two places, and it is worth seeing those two places at once before anything else:

struct Person {
    string name;
    int    age;

    // ─── INSIDE the braces: DECLARATIONS ───
    // No Person:: — the compiler is already inside Person.

    void   setName(string);
    string getName();
    Person();
};          // ← the struct's braces close here


// ─── OUTSIDE the braces: DEFINITIONS ───
// Person:: is now required — nothing out here says which struct.

void Person::setName(string newName) {
    name = newName;
}

string Person::getName() {
    return name;
}

Person::Person() {
    name = "";
    age  = 0;
}

Follow getName across both halves:

WhereWhat is writtenWhy
inside { }string getName();already inside Person — no need to say so
outsidestring Person::getName() {outside now — must say which struct

Same function. The only differences are Person::, and a semicolon in place of a body.

You might reasonably wonder: why write it twice at all? Delete the declaration and the compiler reads string Person::getName() and answers: Person has no member called getName. Delete the definition instead and it answers: getName was promised but never written.

The declaration promises; the definition delivers. You need both, and that is the whole reason the same signature appears twice in every C++ struct you will write.

Turning a definition into its declaration — the four parts

You never have to remember a declaration separately. It is the definition’s first line with two edits. Split that line into four parts and the rule reads itself:

string   Person::   getName()   {
PartWhat it isIn the declaration
stringthe return typekeep
Person::which struct this belongs todrop
getName()name + parameter listkeep
{start of the bodyreplace with ;

Result: string getName();

You might reasonably wonder: why does Person:: disappear? Because inside the braces of struct Person { … }, everything is already known to belong to Person — repeating it would be redundant. Outside those braces the compiler has no idea which struct getName belongs to, so Person:: is how you tell it. Same function, two places, two amounts of context needed.

Careful — you drop Person:: going in, never going out

You might reasonably wonder: if the declaration inside the struct does not need Person::, can I leave it off the definition outside too? No. That is the one place the rule does not run backwards.

Person:: is not decoration. It answers "which struct does this function belong to?" — a question that only answers itself inside the braces.

WhereWhat you writeLegal?What it actually is
Inside struct Person { }void print();✔a declaration
Inside struct Person { }void print(){ … }✔a full definition, written inline
Outside the bracesvoid Person::print(){ … }✔a definition
Outside the bracesvoid print(){ … }✘a free function — unrelated to Person

That last row is not a slightly-wrong member function. It is a different function that happens to share a name. And the compiler will not say so directly — it reports:

error: 'name' was not declared in this scope

A free function has no Person, so name, age, weight and height are simply four undefined variables. The error points at the fields, never at the missing Person::, which is what makes this one hard to debug from the message alone.

Two legal styles — pick one, never mix them

// Style A — declare inside, define outside. What this course uses.
struct Person {
    void print();              // declaration
};
void Person::print(){ … }      // definition — Person:: required


// Style B — define fully inside. No Person:: anywhere.
struct Person {
    void print(){ … }          // declaration and definition at once
};

Both compile. Move a body outside the braces and you must take Person:: with it. Practical 3 and Lecture 4’s List.h/List.cpp both use Style A, so use Style A on the paper.

Person:: is a passport. A function needs one to leave the struct. Inside, it is home and needs nothing.

What may change, and what may not

Parameter names are optional in a declaration. All three of these are legal and mean exactly the same thing, because the compiler reads only the types:

void setName(string newName);   // named
void setName(string n);         // renamed — no link to the definition
void setName(string);           // unnamed — the most common form

A name written there is documentation for a human reader, nothing more. The return type has no such freedom.

The one exception: constructors have no return type at all

Person();                    // declaration
Person::Person() { … }       // definition

There is nothing to keep, because there was never a return type to begin with. A constructor does not return a value — it initialises the object being built. Writing void Person(); does not compile, and it is not a milder mistake than omitting a return type elsewhere; it is the opposite mistake.

Critical Exam Trap • The Return Type Is Not Optional

A declaration is the definition’s first line, ending in ; instead of {. Take the definition’s opening line, drop the ClassName::, drop the body, add a semicolon. Parameter names may be dropped there; the return type may never be.
