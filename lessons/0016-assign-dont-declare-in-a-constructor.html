Assign, don't declare, inside a constructor

Inside a constructor body, never write a type. Write age = 0;, not int age = 0;. The one word int is the difference between the constructor working and the constructor doing nothing at all.

That is the whole lesson. Everything below is why.

What you wrote

person::person(){
    string name = NULL;   // ← declares a brand-new string
    int age = 0;          // ← declares a brand-new int
}

This compiles. It runs. And when it finishes, person's name and age are still garbage — completely untouched.

You might reasonably wonder: but I clearly set age to 0, I can see it right there. You set an age to 0. Not the age.

The two boxes

Two people named Ali in one room. The struct already has an Ali — the member. Writing int age inside the constructor walks a second Ali into the room. From that line onward, "Ali" means the new one. You hand the parcel to the new Ali, then the new Ali walks out and is destroyed when the function ends. The original Ali never got the parcel and never knew anyone was talking to him.

A type in front of a name is the C++ instruction for make a new box. It is not an instruction for put something in the box that already exists.

Why this is worth a whole lesson

Because the compiler will not warn you. Declaring a local variable with the same name as a member is legal C++ — it's called shadowing, and it's occasionally useful, so the language permits it silently. Your program compiles clean and behaves wrongly.

On paper, a marker reading int age = 0; inside a constructor sees a constructor that doesn't construct. It is the single most common way this exam shape loses marks.

The parameterised one has the same fault. string name = newName; makes a new local name and fills it from the parameter. The member is untouched. Correct is name = newName;.

Critical Exam Trap • Declaring Instead Of Assigning

A type in front of a name inside a constructor body creates a new local variable and leaves the member untouched. It compiles cleanly and gives no warning, so nothing tells you it is wrong.

Critical Exam Trap • Every Member, Every Constructor

A constructor's job is to leave no member unset. It is easy to write the parameterised one, set the member the parameter obviously matches, and forget the other. A next that was never set holds rubbish, and the chain it belongs to breaks unpredictably.

Correct (earns marks)Incorrect (loses marks)
Node::Node(int newItem){
  item = newItem;
  next = NULL;
}		 Node::Node(int newItem){
  item = newItem;
}

The one-second check

Before you hand in any constructor, run your eye down the left edge of its body. If any line starts with a type — int, string, Node, * — you have almost certainly just written a bug. A constructor body is nearly all bare assignments.

person::person(){
    name = "unknown";     // ✓ no type
    age  = 0;             // ✓ no type
}

person::person(string newName, int newAge){
    name = newName;       // ✓ no type
    age  = newAge;        // ✓ no type
}

Quick check

A constructor body contains the line int count = 5;, and the struct has a member count. After the constructor finishes, what does the member hold?

Right. The type made a second, local count. It took the 5 and died at the closing brace. The member was never addressed, so it still holds whatever was in that memory. And it compiles cleanly, which is what makes it dangerous.
Look at the left edge of the line. It starts with a type — so that line builds a new box rather than filling the existing one.

Critical Exam Trap • NULL Is For Pointers Only

NULL means "this pointer points at nothing". It is not a general-purpose "empty". A string is not a pointer, so name = NULL; says nothing meaningful — setting a constructor’s members to "empty" needs the right empty for each type.
