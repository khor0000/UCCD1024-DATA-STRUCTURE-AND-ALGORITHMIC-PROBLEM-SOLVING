Lesson 14 of the linked-list crash sequence · The actual test format

Bug-spotting drills

This is the format you confirmed for tomorrow: you'll be handed working-looking List/Node code with one fault planted in it, and asked to find it. Six drills below, each a realistic variant of a function you've now built by hand. Read each one line by line before picking an answer — resist the urge to pattern-match on "insert looks basically right."

Drill 1 — find

Node *List::find(int position) {
    Node *cur;
    if (position > count) return NULL;
    cur = head;
    for (int count=1; count<=position; count++)
        cur = cur->next;
    return cur;
}

What's wrong?

Right. find(1) should take 0 steps (cur already at head) but this version takes 1, landing on position 2 instead — and find(count) walks one past the last real node, risking cur->next on a NULL cur.
Compare against the version you traced in the find(position) lesson: the loop should stop one step earlier than this one does. Count how many times each version's loop body runs for find(1).

Drill 2 — insert, skipping the position-1 case

bool List::insert(int at, int newItem) {
    Node *pre, *cur, *tmp = new Node(newItem);
    if (at < 1 || at > count+1) return false;
    if (!tmp) return false;

    pre = find(at-1);
    cur = pre->next;
    tmp->next = cur;
    pre->next = tmp;
    count++;
    return true;
}

This drops the empty-list and position-1 special cases entirely, going straight to the general case. What actually happens when you call insert(1, 5) on the list 10 → 20?

Right — trace find(0): the guard only checks position > count, so 0 isn't rejected; the loop condition count < 0 is false immediately, so it returns cur = head unchanged. pre = head, and the new node lands at position 2, not position 1.
Trace find(0) by hand using the exact find code from the find(position) lesson — does it return NULL, or something else?

Drill 3 — insert, missing count++

pre = find(at-1);
cur = pre->next;
tmp->next = cur;
pre->next = tmp;
return true;

What's wrong, and what breaks as a result?

Right — the linking itself is fine here, which makes this bug sneaky: the list looks correct if you only print it, but count and the chain have quietly gone out of sync.
Read every line for what's missing, not just what's there — compare line-by-line against the real insert general case.

Drill 4 — insert at position 1, order swapped

if (at == 1) {
    head = tmp;
    tmp->next = head;
    count++;
    return true;
}

What's wrong?

Right — this is the exact ordering trap from the insert-position-1 lesson. The fix is simply swapping the two lines.
Walk it in order: after line 1, what does head equal? Then what does line 2 actually assign to tmp->next?

Drill 5 — remove, freed before relinking

pre = find(from-1);
cur = pre->next;
free(cur);
pre->next = cur->next;
count--;
return true;

What's wrong?

Right — the rule from the remove-general-case lesson: read everything you need from a node before you free it, never after. Swap the free(cur) line to come last.
Look at what free(cur) does to cur, then check what the very next line tries to read from cur.

Drill 6 — remove position 1, head moved too early

if (from == 1) {
    head = head->next;
    count--;
    free(head);
    return true;
}

What's wrong?

Right — this needs a temporary pointer (traditionally called cur) to remember the old head BEFORE head moves, exactly like the remove-position-1 lesson showed.
Ask: by the time free(head) runs, which node does head actually point to — the one that should be removed, or the one that should survive?

If you got every drill right on the first try, you're in good shape for tomorrow. If any took a second guess, ask your tutor to make up two or three more variants of just that one — repetition on the specific pattern you missed is worth more right now than moving forward.
