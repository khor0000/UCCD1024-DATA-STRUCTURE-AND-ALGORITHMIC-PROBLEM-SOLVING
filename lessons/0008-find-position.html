Lesson 8 of the linked-list crash sequence · Traversal

find(position)

find answers one question: "give me a pointer to the Node sitting at position n." Every other List operation — get, set, insert, remove — is built on top of calling find first. Get this one solid and the rest of the operations stop feeling like separate things to memorize.

Back to the treasure hunt. Someone asks you for "stop number 3." You don't teleport there — you start at stop 1 (head) and walk forward, stop by stop, counting as you go, until you've taken enough steps to be standing at stop 3.

The exact code (Lecture 4):

Node *List::find(int position) {
    Node *cur;

    if (position > count) return NULL;
    cur = head;
    for (int count=1; count<position; count++)
        cur = cur->next;
    return cur;
}

You might reasonably wonder: where does count come from on line 4, if (position > count)? It isn't declared anywhere above it. Look at the function's full name: Node *List::find(int position). The List:: means this function runs as a member of a specific List object — and a member function gets silent, automatic access to every field of its own object. No dot, no this->, nothing written. count on line 4 means "the count field belonging to whichever List this call is running on." That's the same count you'd see written as list.count from outside the struct.

Now look at the for loop below it: int count=1 declares a completely different, local count that only exists inside the loop — a coincidence of naming, not the same variable. This loop-local count is really just a step counter; it could have been called i and behave identically.

Two different counts, same name:

Which countWhere it livesWhat it means
Line 4's countthe List object's own fieldhow many nodes are currently in the list
Line 8's counta fresh local variable, born and dying inside the fora step counter — how many loop iterations have run

Positions are 1-indexed: position 1 means head itself, so the loop takes zero steps to get there. Position 2 takes one step (cur = cur->next once), position 3 takes two steps, and so on — the loop runs position - 1 times.

So find(1) returns a pointer straight to head (zero loop iterations). find(3) on this list starts cur at position 1, then runs the loop twice (count goes 1→2, then 2→3), moving cur forward via cur->next each time, ending at position 3.

cur is its own pointer variable — own address, separate from every box it visits, same as cur in the traversal loop. Step through the loop running twice:

find(3) returns cur's final value, 0x540 — the address of box3. The caller now has a pointer straight to position 3, without knowing or caring about any address number itself; you only see the numbers here to trust that the walk actually lands where it should.

The guard if (position > count) return NULL; only checks the upper bound. It trusts the caller to never pass a position below 1 — find(0) or find(-5) isn't guarded against here at all, it would just misbehave. That gap is exactly the kind of thing a "spot the bug" question likes to hide in a variant of this function.

Quick check — on a list with 3 nodes, how many times does the loop body run for find(1)?

Right — position 1 is head itself, so find(1) does no walking at all; the loop condition count < position is already false (1 < 1).
The loop runs position − 1 times. For position 1, that's 1 − 1 = 0 — cur starts at head, which already IS position 1.

Second check — for find(3), how many times does cur = cur->next; execute?

Exactly — position − 1 = 3 − 1 = 2 steps.
The loop runs position - 1 times. What's 3 − 1?

Once find(position) feels mechanical — not memorized, mechanical — insert and remove are just "find the right spot, then relink a couple of pointers."
