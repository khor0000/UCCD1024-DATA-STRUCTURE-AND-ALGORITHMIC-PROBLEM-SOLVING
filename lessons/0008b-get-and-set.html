Lesson 8b of the linked-list crash sequence · Reading & writing an item

get and set

get and set read or overwrite the item at a given position. Both are just find plus one extra line — the only genuinely new idea here is one symbol in get's signature: int &result.

The new idea: a reference parameter

int &result means result isn't a copy of whatever the caller passed in — it's another name for the caller's actual variable. Change result inside the function, and the caller's original variable changes too, because there was only ever one variable, wearing two names.

Two name tags on the same locker. An ordinary parameter is a photocopy of the caller's note, handed to you — scribble on it all you want, the original is untouched. A reference parameter is you and the caller both having a key to the exact same locker. There's no copy. Open it, change what's inside, and the caller sees the change the moment they look.

void addOne(int x) {     // x is a COPY
    x = x + 1;
}
void addOneRef(int &x) { // x is the SAME variable as the caller's
    x = x + 1;
}

int a = 5;
addOne(a);      // a is still 5 — x was a separate copy
addOneRef(a);   // a is now 6 — x WAS a, no copy involved
This & is doing a different job than the & from Lesson 1. There, &x meant "give me x's address" (used at the call site, on a plain variable). Here, & sits inside a function's parameter declaration and means "this parameter is not a copy — it's the caller's own variable." Same symbol, two unrelated jobs, exactly like * back in Lesson 1's declare-vs-dereference note. Nobody calls get(2, &val) with an & at the call site — you just write get(2, val), and the reference is entirely the function signature's doing.

Quick check — after int a = 5; addOneRef(a);, what is a's value?

Right — a reference parameter has no copy step. x and a are the same variable throughout the call.
Compare to addOne (copy) above: addOneRef takes int &x — no copy, x IS a for the duration of the call.

Why get needs this

get's return type is already bool — used up signalling success or failure. But get also needs to hand back the actual item. A reference parameter gives it a second way out: write into result, and the caller's variable holds the answer once the call returns.

bool List::get(int position, int &result) {
	if (position > count) return false;
	result = find(position)->item;
	return true;
}

Calling it: int val; bool ok = list.get(2, val); — after this, ok tells you whether it worked, and val (not a copy — the exact same val) holds the item at position 2.

Same asymmetric guard as find: if (position > count) return false; only checks the upper bound. get(0, val) or get(-3, val) isn't rejected here either — it falls through to find(position)->item, which (per Lesson 8) would misbehave on an out-of-range position. Same bug family, different function.

set: no reference needed

bool List::set(int position, int newItem) {
	if (position > count) return false;
	find(position)->item = newItem;
	return true;
}

set only needs to feed a value in — newItem is a plain, ordinary parameter (a copy is fine, since nothing needs to be handed back through it). Only get needed a reference, because only get needs to send an extra value back out.

Second check — one word: which of get/set actually needs a reference parameter, and which doesn't?

Exactly — get needs to send a value back out (no return value left to use for it), set only needs to receive one.
Ask: which function needs to hand an extra value BACK to the caller, beyond just true/false?

Both get and set lean entirely on find — if find(position) itself still feels shaky, that's worth another look before insert next.
