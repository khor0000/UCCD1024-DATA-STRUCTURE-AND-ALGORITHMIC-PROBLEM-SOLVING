Lesson 10c · Insert — the payload-type question · Q2b

One list, one payload type

Yes — one List definition holds exactly one kind of item, and that is fixed when the program is compiled. A list of Person cannot also hold a double. But you do not write a separate NodeDouble struct to get a double list — you change one line, and the list code itself does not change at all.

This lesson answers the question directly and then tells you exactly how much of it matters for the midterm. It is a short aside on Lesson 10, not a new skill.

A pre-printed form with one blank at the top. The form says “Item type: ______” once, at the top. Every row below just says “the item”. Fill the blank with Person and the whole form is a Person form; fill it with double and every row now means a double. You never reprint the rows — you only ever change the blank at the top.

The one line that decides — type

Your course never writes Person inside Node or List. It writes a nickname, type, and sets that nickname once:

// Node.h  and  List.h  both open with:
using type = Person;          // the ONE line. (older style: typedef Person type;)

struct Node {
    type   item;              // "type", not "Person"
    Node  *next;
    Node(type);
};

using type = Person; means “wherever I write type, read Person.” The compiler swaps it in everywhere before it compiles anything. Change that single line to using type = double; and Node::item is now a double, insert's parameter is now a double, get / set / remove all follow — automatically, because they were all written in terms of the nickname.

What happens to the Node constructor

The constructor is written against the nickname too, so its body never changes. Here is the course's version:

Node::Node(type newItem) {
    item = newItem;      // copy the item into this node
    next = NULL;         // a new node is attached to nothing yet
}
  • Node(type newItem) compiles as Node(double newItem) or Node(Person newItem) — the compiler substitutes the real type.
  • newItem arrives by value: a copy of one whole item (a copy of the number for double; a copy of all the fields for Person).
  • item = newItem; copies it into the node's item field. For double that is a plain number copy. For Person it is = on a struct — a member-by-member copy (Lesson 15a), and a shallow one: the spouse pointer is copied as an address, not followed (Lesson 15).
  • next = NULL; runs for every type — nothing type-specific about it.
The item is copied by value three times on its way into the list:
caller → insert(int at, type newItem) → new Node(newItem) → Node(type newItem) → node.item
Every arrow is a full copy. That is fine for the exam — just know the node ends up holding its own copy of the item, independent of the caller's variable.
You might reasonably wonder: could the constructor just do item = 0;? Only if type is a number. When type = Person, item = 0; is a compile error — a struct has no rule for “become 0”, and Person has no operator= that takes an int. This is the real reason the constructor takes the item as a parameter and writes item = newItem; — that is type assigned to type, the same type on both sides, which always compiles. Type-agnostic code never assigns a literal to item.
The course's Node has no default Node() constructor — only Node(type). So new Node(newItem) is the only way to make a node; new Node on its own would not compile. If you ever wanted a default one that works for any type, you would leave item untouched: Node::Node() { next = NULL; }.

Proof: the insert body never names Person

This is the exact insert you drilled. Read every line and look for the word Person:

bool List::insert(int at, type newItem) {
    Node *pre, *cur, *tmp = new Node(newItem);

    if (at < 1 || at > count+1) return false;
    if (!tmp) return false;

    if (empty())  { head = tmp; count++; return true; }
    if (at == 1)  { tmp->next = head; head = tmp; count++; return true; }

    pre = find(at-1);
    cur = pre->next;
    tmp->next = cur;
    pre->next = tmp;
    count++;
    return true;
}

It is not there. The body only ever moves pointers and copies newItem into a new node. It does not care whether an item is a Person, a double, or an int. That is why, on Day 4, writing insert for an int payload and then for a Person payload was the same code both times — only the alias above the function was different.

Can one program have both a Person list and a double list?

Not from one definition. If you truly need both at once you need two separate list types — two headers, e.g. a ListPerson and a ListDouble, each with its own type alias and its own Node. The professional answer is a C++ template (template<class T> struct List), which stamps out a fresh list type per T on demand. Templates are not in this course — do not use them in the exam.

One exception where the type does matter: the sorted insert, bool insert(type) (add in ascending order). To place an item in order it must compare two items — < for a double, but a member like compareName for a Person. The positional insert you drilled, insert(int, type), never compares anything, so it is completely type-blind. Q2b asks for the positional one.

On paper, for a linked list whose payload is double:

  1. Write the type alias line, the Node struct, and the Node constructor body.
  2. Write the full body of bool List::insert(int at, type newItem) — guard, empty case, position 1, general case.
  3. Underline every place in your constructor and insert body where the word double appears.
reveal answer 
using type = double;

struct Node {
    type   item;
    Node  *next;
    Node(type);
};

Node::Node(type newItem) {
    item = newItem;
    next = NULL;
}

bool List::insert(int at, type newItem) {
    Node *pre, *cur, *tmp = new Node(newItem);

    if (at < 1 || at > count+1) return false;
    if (!tmp) return false;

    if (empty())  { head = tmp; count++; return true; }
    if (at == 1)  { tmp->next = head; head = tmp; count++; return true; }

    pre = find(at-1);
    cur = pre->next;
    tmp->next = cur;
    pre->next = tmp;
    count++;
    return true;
}

Step 3: the word double appears nowhere in the constructor body or the insert body — only in the using line and (as type) in the two parameter lists. That is the whole point: both bodies are identical to the Person version and the int version you already wrote.
