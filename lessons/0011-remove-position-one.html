The whole shape of remove, before any code

remove(from) is insert run backwards: instead of splicing a node in, you splice one out. It does four things, always in this order:

  1. Check the request is real. from must name a position that already exists — 1 to count.
  2. Walk to the node just before the target — unless the target is position 1, which has no "before". That is this lesson.
  3. Re-route. The node before the target points past it, to whatever came after.
  4. Hand the memory back with free() — after saving anything you still need from the doomed node.

This lesson is steps 2–4 for the position-1 case only, where "re-route" just means moving head forward one node.

bool List::remove(int from) {
    Node *pre, *cur;

    if (from < 1 || from > count) return false;   // is the position real?

    if (from == 1) {                              // ← this lesson
        cur = head;         // save the doomed node's address
        head = head->next;  // head skips over it
        count--;
        free(cur);          // hand its memory back
        return true;
    }
    // every other position — next lesson
}

Unhooking the first carriage. To take the front carriage off a train, you first note which carriage is behind it, uncouple, and let the second carriage become the new front. Only then do you haul the old front carriage away — if you scrapped it while it was still coupled, you would lose the rest of the train with it.

Why the guard is > count, not > count+1

insert's guard allowed at up to count+1, because appending one past the end is a real, legal insert. remove has no equivalent — you can only remove a node that already exists, so its upper bound is plain count. Same-looking guard, one fewer, for a real reason.

Critical Exam Trap • Save The Node Before Moving head

cur = head; must run before head = head->next;. head is the only pointer to the node being removed; once head moves, that node is unreachable and cannot be freed. Move head first and free(head) then frees the survivor — the node that should stay — and the real target leaks.

Dangling pointer. After free(cur), cur still holds an address but that memory is no longer yours. Reading or writing through it is a "use after free" bug. The fix is not to avoid cur forever — it is to never touch it again after the free, which is exactly what this function does: free(cur); return true;.
Why free and not delete? Strictly, C++ pairs new with delete. This course's List.cpp genuinely uses free(), so that is what to expect on the paper. Read free(cur) as "hand this node's memory back"; a marker would accept delete cur; in the same spot.

Quick check — two words: what is cur called right after free(cur), still holding an address it no longer owns?

Exactly — a dangling pointer. Touching it after the free is "use after free".
