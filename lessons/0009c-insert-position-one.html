Lesson 9c of the linked-list crash sequence · Insert (part 3 of 4)

insert: position 1, non-empty list

Now there's already a chain, and the new node needs to become the new first stop, pushing the old head one step back:

if (at == 1) {
    tmp->next = head;   // new node's "next" now points at the old head
    head = tmp;         // head now points at the new node instead
    count++;
    return true;
}
Critical Exam Trap • Where The return Line Sits

Every branch of a bool function ends with its own return true;, and that line must be inside the braces and last — after count++;, before the }. Three ways it goes wrong: missing (execution falls through into the code below — for at == 1 that means find(0) and a corrupted list); outside the } (runs unconditionally, so every call returns here and the branches below are dead); or before count++; (the count++ never runs — return ends the function on its own line).

Correct (earns marks)Incorrect (loses marks)
if (at == 1) {
  tmp->next = head;
  head = tmp;
  count++;
  return true;
}		 } return true; // outside
return true; count++; // count++ dead
// or no return at all

Tracing it, address by address

Before either line runs: head (its own address, 0x900) holds 0x500 — box1, item 10. tmp (address 0x904) holds 0x560 — the brand-new box, item 5, next already NULL (set by the constructor, Lesson 6f). Step through both lines:

Full chain preserved: head → new box (5) → box1 (10) → the rest of the chain. Nothing was lost, because tmp->next grabbed head's old value before head itself changed.

Watch it fail: the two lines swapped

Now the exact same two lines, opposite order, from the same starting state:

The result: a one-node loop pointing at itself, and box1 (plus everything after it) still sitting in memory, fully intact — but unreachable. Nothing in the program holds their address anymore. tmp->next = head only works when it runs before head changes, because it needs to read head's old value — the only copy of the old chain's address that exists anywhere.

Order matters because both lines touch the same piece of information (the old chain's starting address) — one line reads it, the other overwrites it. Whichever runs second sees whatever the first one left behind. This exact ordering mistake is a classic "spot the bug" candidate.

Quick check — inserting at position 1 into a non-empty list, why must tmp->next = head happen before head = tmp?

Right — head is your only pointer to the old chain. Overwrite it first and that chain's address is gone before tmp ever borrows it.
Look at the "watch it fail" trace above: head is the one variable holding the old chain's address. Whichever line reads it second gets the wrong value.

Second check — a few words: in the broken (swapped) order, what does tmp->next end up pointing at?

Right — itself. head had already been changed to tmp's address before tmp->next = head ran, so tmp->next copies that new value: its own address.
Re-read step 2 (broken) above — by the time that line runs, what does head currently hold?
